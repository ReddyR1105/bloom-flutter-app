The required introductory AI learning component
Required for undergraduates and graduates: implement one local prediction, recommendation, or adaptive hint that uses relevant input to produce a suggestion and a truthful explanation. A static decoration, ordinary aggregate alone, chatbot mockup, or using an AI coding assistant does not satisfy this requirement.

Best first-time route: write transparent scoring rules, a history-based estimate, or an adaptive prewritten-hint selector. These qualify for this assignment's introductory AI learning component because students practice decision logic, evaluation, and responsible use. Label the feature rule-based smart helper if it is rules or statistics; do not claim a trained or generative model. A simple example-based nearest-neighbor method also qualifies but is not mandatory, including for graduates.

Use existing local records/preferences or clearly labeled fictional bundled examples. No extra screen, third relational entity, API key, paid tool, cloud database, remote inference, or model-training service is required.
Show the suggestion, its inputs/reason, and a way to dismiss or override it. Applying a value does not commit a record until the user explicitly saves/starts/submits. Hint helpers may reveal a hint only after an explicit Reveal action.
Show actionable no-data/no-match and invalid-input feedback. Tie-breaking and any thresholds must be documented. Never invent confidence percentages or medical/safety claims.
Recompute when relevant local inputs change; demonstrate networking-disabled operation and restart with the saved inputs. A prediction is not a guarantee, and a recommendation need not always win.
All other core and graduate requirements remain in force. One shared helper can provide evidence for multiple team members, but each must explain their own role and the reasoning. Mixed-level teams use the same feature; graduate members provide the additional comparison/testing evidence.

Critical thinking is part of the implementation
Define usefulness: state the user decision and a modest, measurable success criterion before coding. An engaging feature must help a task, not just display an "AI" badge.
Choose inputs: justify each field, exclude irrelevant/sensitive fields, and explain how duplicates, edited records, or biased fictional data could mislead the result.
Defend the method: explain weights, history windows, clamps, prerequisites, and tie rules. Name an alternative and why you did not choose it initially.
Challenge your solution: construct a counterexample where the helper gives a poor or unhelpful suggestion. Explain why, then revise the method or explicitly preserve and disclose the limitation.
Compare fairly: use a simple baseline on the same valid inputs. A complex method is not automatically better; keep the simpler one when the evidence supports it.
Preserve agency: show how a user can reject the result and how an invalid/no-data state avoids misleading output. Distinguish a checked estimate from a guarantee.
Undergraduate: implement, explain, and challenge
Build one helper and one simple comparison baseline (a constant, last value, or neutral ordering is sufficient). Record at least five distinct cases: normal, empty/insufficient input, invalid input, a boundary/tie/outlier case appropriate to the method, and a counterexample. Manual reproducible cases are acceptable; automated tests are welcome but are not a new undergraduate unit-test quota.

For each case, record case ID, inputs, expected behavior, actual behavior, and pass/fail. For valid comparison cases, record both outputs and the reference outcome; for no-data/invalid cases assess correct feedback rather than inventing numeric scores. Show the metric and sample size, one limitation, and a justified revision or decision to retain the method. Explain all six critical-thinking decisions above.

Use absolute error for numeric estimates; matches out of cases for labeled recommendations; relevance and spoiler checks for hints. Prefer fictional/consented cases with known reference outcomes. A tiny sample demonstrates the method; it does not establish broad accuracy or causal benefit.

Graduate: compare, test, and justify
Complete the undergraduate helper and reasoning requirements. Compare the two approaches (the helper and a meaningful baseline count) on the same at least five held-out valid cases, separate from cases used to tune rules, weights, or example labels. In addition, retain the normal/empty/invalid/boundary/counterexample checks; held-out cases may overlap the normal and counterexample checks if they were genuinely reserved, but invalid cases do not count as valid scored cases.

Freeze methods before evaluation, report both metrics/sample sizes, inspect errors, and justify the final method. If you revise after viewing held-out results, treat those cases as development data and reserve a new held-out set for the final comparison. For chronological estimates, inputs must precede the reference outcome. Use a fake clock or controlled fixtures where relevant.

Include helper tests within the existing minimum 10 meaningful unit tests plus widget/integration tests and coverage report; this does not add another 10-test quota. Show a widget case for explanation/override or no-data feedback and an offline/restart integration case. Apply the required state-management, repository/DI, and UI/domain/data boundaries to the helper.
