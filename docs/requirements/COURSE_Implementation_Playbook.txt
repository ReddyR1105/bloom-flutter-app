06 · Required introductory AI / smart-helper lab
Required for both pathways · topic-linked · offline
Every team must implement one topic-linked smart helper in its app. Rules/statistical estimates or a small example-based ML method qualify for this introductory learning component; label the method accurately rather than claiming rules are a trained model. An ordinary aggregate alone or use of an AI coding assistant does not satisfy the runtime feature requirement.

Think tiny smart helper, not chatbot: one suggestion card, explanation, and Apply / Not now (or Reveal / Not now) choice are enough. No training service, API key, subscription, extra screen, or third SQLite entity is needed. Read the required feature menu, critical-thinking decisions, and pathway acceptance criteria. Plan it in the proposal, build after the core data slice works, and complete it by the October 23 checkpoint.
Two approachable ways to explore AI ideas
Start here / no ML library
Explainable rules and recommendations
Use a few weights, a recent-history average, or a prewritten hint lookup. This introduces inputs, ranking, prediction, explanations, and evaluation. Describe it as a rule-based smart helper, not a trained model or generative AI. Rules are written by you; an average alone does not learn a model.

Optional next step / tiny example-based ML
Find the most similar example
For a recommendation topic, bundle 6–10 fictional, labeled examples in Dart or local JSON. Each pairs a small feature vector (such as a category encoded as 0/1 flags and a preference) with a recommended choice. Find the example with the smallest mismatch distance and return its label. This is a simple one-nearest-neighbor classifier: it predicts from labeled examples rather than a hand-written answer rule. It needs no gradient training, cloud service, or ML package; it is not a language model.

Give categorical flags equal weight, scale numeric features if used, choose ties deterministically, and explain which example matched. Add an explicit no-match/out-of-scope threshold and an empty-example state. Store labeled examples locally; never call an exact-match lookup alone a learned model.

Tiny ML fixture: encode a mission request as [art preference, study preference, wants a short task], each 0 or 1. A labeled example [1, 0, 1] recommends "Sketch a campus detail"; [0, 1, 1] recommends "Try a study spot." For a new input [1, 0, 0], the sum of absolute flag differences is 1 versus 3, so the nearest example recommends the sketch. For this fixture, accept distances up to 1; otherwise show "No close example." With equally close examples, choose the lowest stable example ID and disclose the tie. This is a fictional classification demonstration, not a claim about every student's preferences.

A small build-and-play loop
Pick one useful decision: choose the topic's helper below, not an entire AI assistant. Name the benefit: fewer taps, a clearer estimate, or a hint that keeps the game moving.
Prepare a few safe examples: use existing SQLite history or fictional bundled data. Choose only fields already available; do not collect sensitive information to make the feature seem smarter.
Write one pure Dart function: inputs in, suggestion plus explanation out. Keep it outside widgets. Reuse the existing state and storage boundaries.
Show one card in an existing screen: display "Suggested, not guaranteed," the reason, and Apply / Not now. Applying a suggestion fills a control; only the user's explicit Save/Start/Submit action commits it.
Play detective with the result: try a normal input, no history, a tie, invalid data, and one deliberately bad suggestion. Use the topic's tiny numeric or ranking fixture to check exact outputs.
Try feedback without hype: ask a peer whether the suggestion helped. If using feedback, save a preference/rating on an existing record or in SharedPreferences and show exactly how it affects the next result. A rating button that does not change anything is not learning.
Honest evaluation: reserve a few examples that were not used to choose rules, weights, or example labels. For estimates, show absolute error in real units; for choices, show matches out of tested cases; for hints, check relevance and spoiler avoidance. Report a small demonstration sample as a demonstration, not proof of accuracy for everyone. No invented confidence percentages.

Predict
Estimate the next meal cost or personal trip duration from earlier local records. Suggest a habit target or focus duration without claiming a behavioral or health prediction. Show inputs, units, and limits.

Investigate
Review puzzle attempts, attended event tags, or planned-versus-actual trip times. Use the findings to select a useful hint or explain a trend; do not claim a cause from a few observations.

Recommend
Rank a mission, local event, or user-entered workout plan by explicit preferences. Explain the ranking and allow dismissal or override; workout rankings organize choices, not medical or exertion advice.

Frame a question: name the user decision, the local input fields, expected output, and a measurable success criterion in the proposal.
Prepare local data: use consented or clearly labeled synthetic samples in SQLite. Do not upload app-user records to external AI or data services. Permitted GitHub/ClickUp/YouTube coordination and submission do not authorize cloud app storage or remote inference.
Implement and compare: build the helper using a history-based estimate, scoring rules, or a simple on-device model. Add a separate comparison baseline such as the last value, a fixed duration, or neutral ID ordering. Keep calculation logic separate from rendering.
Evaluate: compare predicted and actual values, or evaluate ranked recommendations with labeled examples. Test normal, empty-history, invalid-input, and outlier cases. Report sample size, metric, and limitations.
Design safe feedback: show an explanation and an explicit "not enough data" state. Do not invent confidence scores. Fitness and trail suggestions are educational demonstrations, not medical or safety advice.
Document and demonstrate: show input → analysis → explanation → feedback → updated result. Record reasoning and evaluation in required AI_FEATURE.md; maintain AI_Usage_Log.md separately only for AI development assistance.

07 · Kanban: finish together
Visualize work · limit work in progress · improve flow
Kanban is a way to manage and improve the flow of work, not just a colorful task board. Make your workflow, entry/exit rules, and work-in-progress (WIP) limits explicit. Pull new work only when there is capacity, and finish or unblock existing work before starting more.

Review / test

Peer review + offline restart test.

Settings persist after restart.
Task card: title, owner, due date, acceptance criteria, dependency, and GitHub issue/PR link. Example: "Adding a valid meal saves once and still appears after an offline restart."
Blocked work: flag the task in its current column, record the reason and next action, and assign someone to help. Blocked tasks still count toward WIP.
Daily check-in: spend five minutes discussing what can finish, what is aging, and what is blocked. Review and testing are real work, not a dumping ground.
Measure flow: WIP = started but unfinished tasks; throughput = tasks finished per day; work item age = elapsed time since starting an unfinished task; cycle time = elapsed time from start to finish. Log a small daily sample and discuss one improvement.

🔄 Step 5: Syncing with Team
🔄 Pull & Merge Commands

📋
Copy

# Update your feature branch with main changes

# If conflicts occur, resolve them in your editor
# Then add and commit the resolved files
git add .

# Push updated branch
git push origin feature/your-feature
🔀 Step 6: Pull Requests
Create PR: On GitHub, click "New Pull Request" for your branch
Write Description: Explain what the PR does and why
Request Review: Tag team members for code review
Address Feedback: Make requested changes and push updates
Merge: After approval, merge into main branch
💡 Pull Request Best Practices:

• Include screenshots for UI changes
• Link to related issues or tasks
• Test thoroughly before requesting review
• Keep PRs focused (one feature per PR)
• Respond to review comments promptly
